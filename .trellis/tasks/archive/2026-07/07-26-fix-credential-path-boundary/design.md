# Design

## Boundary 1: origin-scoped Zotero authentication

`ZoteroRemote` keeps one pooled `reqwest::Client`, but request construction is split by
authority:

- `zotero_request(method, endpoint)` adds `zotero-api-key` and is used only for URLs
  generated by `self.endpoint(...)`.
- `external_upload_request(upload_url)` validates the URL policy and creates a request
  directly from the pooled client without the key header.

The production constructor sets no insecure exception. The existing test-only explicit-base
constructor may allow plain HTTP only when the upload host is loopback, so the recognized
`tiny_http` adapter can exercise the whole four-request upload flow without weakening runtime
policy. Scheme validation happens before `.send()` and returns `ZotError::InvalidInput` with a
stable attachment-upload URL code.

## Boundary 2: validated workspace identity

`WorkspaceName` owns the kebab-case invariant and implements parsing/display/as-ref behavior.
Paths are constructed only from `&WorkspaceName`; the raw `path_for(&str)` surface becomes
private typed helpers. `WorkspaceStore::save` parses `Workspace.name` before persistence so a
public `Workspace` struct cannot bypass validation.

The CLI parses each raw workspace argument at the command boundary and passes the typed value
through load/delete/RAG operations. Existing output continues to use the original safe string.

## Filesystem containment

The store creates the root where creation is expected, canonicalizes it, then verifies the
candidate's canonical parent equals that root. For an existing candidate, canonicalizing the
candidate also detects a file symlink/reparse target whose resolved parent is outside the root.
Read/open operations reject such targets before reading TOML or opening SQLite. Atomic TOML
save keeps its current temp-file-in-root and persist behavior; replacing an existing leaf does
not follow that leaf.

The same store-owned helper constructs and validates `<name>.idx.sqlite` for
`WorkspaceRagStore::open`. The shared `.md_cache.sqlite` path is unchanged.

## Compatibility And Rollback

- Valid workspace names and on-disk names are unchanged; invalid legacy filenames remain
  ignored by list and are no longer directly addressable.
- API method signatures inside this workspace become typed; all repository call sites and tests
  are migrated in one atomic change.
- Rollback is the task commit. There is no data migration and no valid workspace file rename.
- Restoring credential-bearing external uploads is not an acceptable partial rollback.
